## 07/21 — 문법 기초

**Q4. 슈퍼클래스 상속과 인터페이스 구현의 차이는?**
A. 상속은 단일(하나만), 인터페이스는 다중 구현 가능

**Q5. 로컬 변수와 전역 변수 접두사는?**
A. 로컬 lv_, 전역 gv_

**Q6. READ TABLE과 itab[ ]의 가장 큰 차이는?**
A. READ TABLE은 없어도 sy-subrc로 확인 가능(안전), itab[ ]는 없으면 예외(덤프) 발생

**Q7. itab[ ]에서 대상이 없을 때 sy-subrc는 갱신되는가?**
A. 아니오, 예외가 발생해 갱신되지 않음

**Q8. CX로 시작하는 클래스는 무엇을 뜻하는가?**
A. Exception Class(예외 클래스)

**Q9. 예외처리 3단 구조 키워드는?**
A. TRY / CATCH / ENDTRY

**Q10. 부모 예외 클래스로 CATCH해도 자식 예외를 잡을 수 있는 이유는?**
A. 예외 클래스도 상속 관계(다형성)이기 때문

**Q11. 예외 객체에서 메시지 텍스트를 가져오는 메서드는?**
A. get_text( )

**Q12. CREATE OBJECT 대신 쓰는 최신 객체 생성 문법은?**
A. NEW #( ) 또는 NEW 클래스명( )

**Q13. NEW #( )의 #은 무엇을 뜻하는가?**
A. 타입 추론(Type Inference)

**Q14. 단 건 조회 신문법 SELECT 키워드는?**
A. SELECT SINGLE

**Q15. 다 건 조회 시 INTO 절 형식은?**
A. INTO TABLE @DATA(내부테이블)

**Q16. VALUE로 구조체 전체를 그대로 대입할 수 있는가?**
A. 없음, 필드명=값 형식으로 지정해야 함

**Q17. VALUE로 내부테이블 생성 시 테이블 타입에 반드시 필요한 것은?**
A. 키(WITH EMPTY KEY 또는 WITH KEY)

**Q18. ASSIGN + FIELD-SYMBOL로 내부테이블 행을 CLEAR하면 원본은?**
A. 원본 자체가 직접 변경됨(참조이므로)

## 07/22 — 필드심볼 / Control Break / CDS 언어

**Q19. 필드심볼이란?**
A. 변수/구조체/내부테이블을 동적으로 참조하는 문법

**Q20. LOOP AT ... INTO와 ASSIGNING의 차이는?**
A. INTO는 복사(원본 변경 안됨), ASSIGNING은 참조(원본 직접 변경)

**Q21. 문자열 변수명으로 실제 변수를 동적 연결하는 문법은?**
A. ASSIGN (변수명) TO <fs>.

**Q22. 필드심볼 연결 해제 명령어는?**
A. UNASSIGN

**Q23. ASSIGN COMPONENT의 용도는?**
A. 구조체의 특정 필드(고정/동적명)를 필드심볼에 연결

**Q24. AT END OF는 언제 실행되는가?**
A. 그룹(정렬 기준 필드)의 마지막 행에서

**Q25. AT END OF 사용 전 필수 작업은?**
A. 해당 필드로 SORT

**Q26. AT END OF 안의 SUM.은 어떤 필드에 작용하는가?**
A. 숫자형 필드를 그룹 합계로 변경

**Q27. CDS에서 로그인 언어 조건을 거는 문법은?**
A. Language = $session.system_language

**Q28. [1:Language = 'X']와 같은 문법의 의미는?**
A. 조건에 맞는 항목 정확히 1건만 필터링

## 07/23 — CDS 다단계 뷰 / 집계

**Q29. CDS를 여러 단계로 나눠 설계하는 이유는?**
A. 재사용성, 유지보수성 향상 (역할 분리)

**Q30. I_DomainFixedValueText 사용 시 필터링 조건 2가지는?**
A. SAPDataDictionaryDomain, Language

**Q31. CASE+SUM 집계 결과를 정수형으로 변환하는 함수는?**
A. CAST( ... AS abap.int4 )

**Q32. GROUP BY에 나열해야 하는 필드는?**
A. 집계함수로 감싸지 않은 모든 select 필드

**Q33. 클래식 ABAP에서 도메인 고정값 텍스트를 가져오는 함수모듈은?**
A. DD_DOMVALUES_GET

**Q34. fldate에서 연도/월을 추출하는 함수는?**
A. SUBSTRING(fldate, 1, 4) / SUBSTRING(fldate, 5, 2)

## 07/24 — S/4HANA·C/4HANA / RAP 기본구조

**Q35. S/4HANA와 C/4HANA 차이는?**
A. S/4는 ERP(내부업무), C/4는 CRM(고객관리, Cloud 전용)

**Q36. ABAP Cloud에서 사용 가능한 오브젝트는?**
A. Cloud에서 Release(허용)된 오브젝트만

**Q37. Interface View / Root View / Projection View 순서와 역할은?**
A. Interface(테이블 참조)→Root(Behavior 연결)→Projection(UI 노출)

**Q38. Root View 생성시 defineRootViewEntity의 참조 대상은?**
A. Interface View (또는 테이블)

**Q39. Projection View 생성시 defineProjectionView의 참조 대상은?**
A. Root View

**Q40. @Metadata.allowExtensions: true의 역할은?**
A. Metadata Extension으로 UI 확장 허용

**Q41. Metadata Extension의 목적은?**
A. 로직과 UI 표현(라벨/순서 등) 분리

**Q42. Service Definition과 Service Binding 차이는?**
A. Definition은 노출할 뷰 정의, Binding은 OData로 실제 활성화(Publish)

**Q43. Behavior에서 lock master의 역할은?**
A. 트랜잭션 잠금(Lock)의 기준 엔티티 지정

**Q44. authorization master (instance)의 역할은?**
A. 인스턴스 단위 권한체크 기준 지정

**Q45. etag master의 역할은?**
A. 동시수정 충돌 방지(낙관적 동시성 제어) 기준 필드 지정

**Q46. strict(2)의 의미는?**
A. RAP 구현 검증을 엄격 모드(2단계)로 적용

**Q47. Root Behavior의 create/update/delete와 Projection Behavior의 use create/update/delete 관계는?**
A. Root는 구현, Projection은 그 기능을 노출(사용)

**Q48. field(numbering:managed)의 의미는?**
A. 해당 키필드를 RAP가 자동 채번

**Q48-1. Define Table과 Transparent Table의 차이는?**
A. Define Table=Eclipse(ADT)에서 생성(Cloud 방식), Transparent Table=SE11에서 생성(클래식 방식)

**Q48-2. Projection View와 Metadata Extension의 역할 차이는?**
A. Projection View=노출 필드/Text/Value Help 등 정의, Metadata Extension=Fiori UI(LineItem/Facet/Header 등) 정의

**Q48-3. OData V2와 V4의 기본 차이는?**
A. V2=기존 버전(기본 서비스 제공), V4=최신 버전(Draft 등 RAP 최신기능 지원)

## 07/27 — 텍스트연결 / EML

**Q49. Root+Projection 모두 선언 vs Projection만 선언의 차이는?**
A. 둘 다: 입력 가능/ Projection만: 조회 전용

**Q50. Association 결과에서 로그인 언어 1건만 가져오는 문법은?**
A. _Assoc[1:Language = $session.system_language].필드

**Q51. EML READ에서 FIELDS(...)와 ALL FIELDS 차이는?**
A. 지정필드만 vs 전체필드

**Q52. %key, %tky, %pky 차이는?**
A. %key=DB키, %tky=트랜잭션키, %pky=부모키

**Q53. EML CREATE의 %cid는 무엇의 약자이며 역할은?**
A. Client ID의 약자. 새 데이터 생성 요청을 구분하는 임시 ID

**Q54. %control-필드 = '01'의 의미는?**
A. 해당 필드값을 실제 반영하겠다는 표시(00은 미반영)

**Q55. MODIFY ENTITIES 후 실제 DB반영을 위해 필요한 명령은?**
A. COMMIT ENTITIES

**Q56. UPDATE1(DB Key 직접)보다 UPDATE2(%tky 이용)가 안전한 이유는?**
A. RAP 트랜잭션 상태와 정확히 일치하는 키를 사용하기 때문

**Q57. DELETE 시 delete_emps는 보통 무엇으로부터 생성하는가?**
A. READ ENTITIES 결과(result_emps)를 CORRESPONDING

**Q58. @ObjectModel.text.element의 역할은?**
A. 코드필드에 대응 텍스트필드 지정, 코드 변경시 텍스트 자동갱신

**Q59. @UI.headerInfo의 title/description은 무엇을 나타내는가?**
A. Object Page 헤더의 제목/부제목 필드

## 07/28 — Action / 메시지 / Field Control / Value Help

**Q60. Metadata에서 버튼(Action)을 연결하는 타입은?**
A. type: #FOR_ACTION

**Q61. Behavior에서 Action 선언 기본형은?**
A. action <이름> result[0..1] $self;

**Q62. Projection에서 Root의 Action을 노출하는 문법은?**
A. use action <이름>;

**Q63. Action 구현시 readonly 필드를 수정하려면?**
A. IN LOCAL MODE 사용

**Q64. Action 결과를 화면에 즉시 반영하려면 result에 무엇을 채우는가?**
A. %tky, %param

**Q65. 성공/정보 메시지를 화면에 출력하는 구조는?**
A. reported-<Entity> + new_message(...)

**Q66. 저장/실행을 막으려면 메시지 외에 추가로 채워야 하는 구조는?**
A. failed-<Entity>

**Q67. Value Help를 연결하는 어노테이션은?**
A. @Consumption.valueHelpDefinition

**Q68. @ObjectModel.resultSet.sizeCategory: #XS의 역할은?**
A. 데이터 적음을 명시, 드롭다운 형태로 표시 유도

**Q69. Facet의 targetQualifier와 필드의 qualifier 관계는?**
A. 값이 일치해야 해당 필드가 그 Facet에 표시됨

## 07/29 — Search / Determination / Validation / 권한

**Q70. 백엔드/프런트 오류로그 TCODE는?**
A. 백엔드 /IWBEP/ERROR_LOG, 프런트 /IWFND/ERROR_LOG

**Q71. CDS를 검색가능하게 만드는 View레벨 어노테이션은?**
A. @Search.searchable: true

**Q72. 검색 기본 대상 필드 지정 어노테이션은?**
A. @Search.defaultSearchElement: true

**Q73. Determination과 Validation의 핵심 차이는?**
A. Determination=기본값 설정, Validation=유효성 검증(실패시 저장 차단)

**Q74. 저장시 실행 순서는?**
A. Determination → Validation → DB저장

**Q75. Validation 실패시 반드시 채워야 하는 2가지는?**
A. reported-Entity(메시지), failed-Entity(대상키)

**Q76. get_instance_authorizations와 get_instance_features 차이는?**
A. Authorizations=사용자 권한 제어, Features=데이터 상태별 기능/필드 제어

**Q77. 특정 사용자만 삭제 가능하게 하는 코드에서 쓰는 필드는?**
A. %delete = if_abap_behv=>auth-unauthorized

**Q78. 행 전체 수정 불가 설정값은?**
A. %features-%update = if_abap_behv=>fc-o-disabled

**Q79. 특정 필드만 읽기전용 설정값은?**
A. %features-%field-필드 = if_abap_behv=>fc-f-read_only

**Q80. Behavior에서 동적 기능제어 사용을 위한 선언은?**
A. update ( features : instance );

## 07/30 — Draft / Numbering / Side Effect

**Q81. Draft 기능의 목적은?**
A. 편집중 내용을 임시테이블에 저장, Activate시 실제DB 반영

**Q82. Draft 활성화를 위한 Root Behavior 선언 2가지는?**
A. with draft; / draft table <테이블>;

**Q83. Edit/Activate/Discard/Resume 각각의 역할은?**
A. Edit=편집시작, Activate=실저장, Discard=취소, Resume=이어서편집

**Q84. determination on modify와 on save의 실행 시점 차이는?**
A. on modify=Draft생성시, on save=Activate(실저장) 직전

**Q85. Draft 상태 여부를 판별하는 필드는?**
A. %is_draft (mk-on이면 Draft)

**Q86. Early Numbering과 Late Numbering의 채번 시점 차이는?**
A. Early=생성(Draft) 즉시, Late=Activate 저장 시점

**Q87. Early/Late Numbering이 각각 주로 쓰이는 OData 버전은?**
A. Early=V4, Late=V2

**Q88. Early Numbering 구현 메서드명은?**
A. earlynumbering_create

**Q89. Late Numbering 구현시 상속받는 클래스는?**
A. cl_abap_behavior_saver (adjust_numbers 재정의)

**Q90. Side Effect의 목적은?**
A. 특정 필드 변경시 연관 필드 자동 재계산+화면 갱신

**Q91. Side Effect 구현시 Root Behavior에 필요한 선언 2가지는?**
A. determination ... on modify { field X; } / side effects { field X affects field Y; }

**Q92. Side Effect를 Projection Behavior에도 선언해야 하는 이유는?**
A. 화면에서 자동 갱신을 인식하도록 하기 위해
